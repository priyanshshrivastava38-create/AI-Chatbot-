# Prism HTTP API reference

Every claim below is read out of the source in this repository. File references are given
per endpoint so you can verify them; nothing here is inferred from a spec.

- Base URL: whatever host the app runs on (`http://localhost:3000` in development).
- All request bodies are `application/json` unless stated otherwise.
- All handlers live in `src/app/api/**/route.ts` and are wrapped by `route()` from
  `src/lib/errors.ts`, so thrown errors always leave through one sanitising path.

## Endpoint index

| # | Method | Path | Auth | Purpose |
|---|--------|------|------|---------|
| 1 | `POST` | `/api/chat` | yes | Send a user turn, stream the reply (SSE) |
| 2 | `POST` | `/api/chat/regenerate` | yes | Drop the last assistant reply, stream again (SSE) |
| 3 | `POST` | `/api/chat/stop` | yes | Cancel an in-flight generation |
| 4 | `GET` | `/api/conversations` | yes | List / search conversations |
| 5 | `POST` | `/api/conversations` | yes | Create a conversation |
| 6 | `GET` | `/api/conversations/{id}` | yes | One conversation + its messages |
| 7 | `PATCH` | `/api/conversations/{id}` | yes | Rename / switch model |
| 8 | `DELETE` | `/api/conversations/{id}` | yes | Delete a conversation and its files |
| 9 | `GET` | `/api/conversations/{id}/export` | yes | Download Markdown or JSON |
| 10 | `POST` | `/api/attachments` | yes | Upload a text file (multipart) |
| 11 | `GET` | `/api/models` | yes | Model catalogue + limits |
| 12 | `GET` | `/api/preferences` | yes | Read effective preferences |
| 13 | `PATCH` | `/api/preferences` | yes | Write preferences |
| 14 | `GET` | `/api/usage` | yes | Token / message analytics |
| 15 | `POST` | `/api/auth/register` | no | Create an account |
| 16 | `GET`/`POST` | `/api/auth/[...nextauth]` | mixed | Auth.js v5 owned routes |

There is **no** `GET /api/attachments`, no attachment download endpoint, and no
`PUT`/`POST` handler on `/api/conversations/{id}`. `/api/attachments` and
`/api/conversations/{id}/export` implement only the verbs listed above; any other method
returns `405` from the framework, not from application code.

## Authentication

`src/lib/auth.ts` configures Auth.js v5 with a **credentials provider** and
`session.strategy = "jwt"`. Consequences for API clients:

- Auth is a **cookie**, not a bearer token. The session cookie is `next-auth.session-token`
  (or `__Secure-next-auth.session-token` under HTTPS). There is no API-key mechanism.
- Session lifetime is hard-coded: `AUTH_SESSION_MAX_AGE_SECONDS = 30 * 24 * 60 * 60` (30 days).
- `AUTH_SECRET` signs/encrypts the JWT; `src/lib/env.ts` requires at least 16 characters.
- Login pages are `pages.signIn = "/login"` and `pages.error = "/login"`.
- Every endpoint in the table above except `/api/auth/*` calls `requireUser()`
  (`src/lib/session.ts`), which throws `UnauthorizedError` → **401**:

```json
{ "error": { "code": "unauthorized", "message": "Authentication required" } }
```

- Ownership: conversation lookups go through `findOwnedConversation(userId, id)`
  (`src/lib/conversations.ts`), which filters on `{ id, userId }` together. A foreign id and
  a nonexistent id both produce the same **404** `not_found` — ownership is never leaked.
- Sign-in throttling lives in the `authorize()` callback: key `login:<email>:<ip>`,
  **10 attempts per 5 minutes**. When exceeded, `authorize` returns `null`, so Auth.js
  redirects to `/login?error=CredentialsSignin` — it does *not* return a 429 JSON body.
  Unknown email and wrong password are also indistinguishable (both `null`).

### Getting a cookie with curl (for the examples below)

```bash
BASE=http://localhost:3000
JAR=cookies.txt

# 1. fetch the CSRF token (sets the csrfToken cookie and prints { csrfToken: "..." })
CSRF=$(curl -s -c "$JAR" "$BASE/api/auth/csrf" | sed 's/.*"csrfToken":"\([^"]*\)".*/\1/')

# 2. POST the credentials to the Auth.js callback, reusing the same cookie jar
curl -s -b "$JAR" -c "$JAR" -X POST "$BASE/api/auth/callback/credentials" \
  --data-urlencode "csrfToken=$CSRF" \
  --data-urlencode "email=demo@example.com" \
  --data-urlencode "password=Demo1234" \
  --data-urlencode "callbackUrl=$BASE/chat" -o /dev/null -w '%{http_code}\n'

# 3. confirm the session
curl -s -b "$JAR" "$BASE/api/auth/session"
```

Anything under `/api/auth/*` other than `/api/auth/register` is generated by Auth.js itself
(`src/app/api/auth/[...nextauth]/route.ts` re-exports `handlers` verbatim). Its subpaths —
`signin`, `signin/credentials`, `callback/credentials`, `signout`, `session`, `csrf`,
`providers`, `verify-request`, `error` — follow Auth.js behaviour and its own response shapes,
not the envelope documented below.

## Error envelope

`toErrorResponse()` in `src/lib/errors.ts` produces exactly this shape for every failure
**before** a response body is streamed:

```json
{ "error": { "code": "validation_failed", "message": "Invalid request",
             "details": [ { "path": "content", "message": "Message cannot be empty" } ] } }
```

`details` is present only for validation failures. Codes and statuses:

| Status | `code` | Thrown by |
|--------|--------|-----------|
| 400 | `bad_request` | `AppError` default |
| 400 | `missing_conversation` | `api/attachments` — no `conversationId` field |
| 400 | `missing_file` | `api/attachments` — no `File` part named `file` |
| 400 | `empty_file` | `lib/uploads.ts` — 0-byte upload |
| 400 | `invalid_upload_path` | `lib/uploads.ts` — resolved path escapes `UPLOAD_DIR` |
| 400 | `model_not_allowed` | `api/preferences` PATCH, `api/conversations/[id]` PATCH |
| 401 | `unauthorized` | `lib/session.ts` `requireUser()` |
| 404 | `not_found` | `findOwnedConversation()` — "Conversation not found" |
| 409 | `generation_in_progress` | `api/chat`, `api/chat/regenerate`, `lib/ai/stream-response.ts` |
| 409 | `nothing_to_regenerate` | `api/chat/regenerate` and `deleteLatestAssistantTurn()` |
| 413 | `file_too_large` | `lib/uploads.ts` — above `MAX_UPLOAD_BYTES` |
| 415 | `invalid_encoding` | `api/attachments` — body not `multipart/form-data` |
| 415 | `unsupported_media_type` | `lib/uploads.ts` — extension or declared MIME rejected |
| 415 | `binary_file` | `lib/uploads.ts` — NUL byte in the first 1 KB |
| 422 | `validation_failed` | `ValidationError` from `readJsonBody` / `parseInput` / `parseSearchParams`; also raw `ZodError` |
| 429 | `rate_limited` | `lib/api.ts`, `api/chat`, `api/chat/regenerate`, `api/auth/register` — adds `Retry-After` (seconds) |
| 500 | `server_misconfigured` | `EnvConfigError` (message logged, never returned) |
| 500 | `internal_error` | any other uncaught value ("Something went wrong. Please try again.") |
| 502 | `provider_error` | `ProviderError` — see the note below |

Two statuses in that table are effectively unreachable today, and the code says so:

- `403 forbidden`: `ForbiddenError` is **defined** in `src/lib/errors.ts` but never thrown
  anywhere in `src/`. Ownership failures surface as `404 not_found`.
- `502 provider_error`: every `ProviderError` is raised inside the streaming path and caught
  before it can reach `toErrorResponse` — `run-turn.ts` converts it into an SSE `error` event,
  `context.ts`/`auxiliary.ts` swallow it into a fallback. So provider failures arrive as
  **HTTP 200 + an `error` event**, not as 502.

Unknown request-body fields are rejected (the body schemas use `.strict()`), and the
resulting `422` names the offending path. Unknown *query* parameters are silently ignored
(`parseSearchParams`/`parseInput` feed a plain object to non-strict schemas).

## Rate limiting

`src/lib/rate-limit.ts` is a **process-memory** limiter: a `Map<key, {hits: number[], lastSeen}>`
of request timestamps, pruned to those inside `windowMs` (default 60 000 ms) on every call.
When a key blocks, `retryAfterMs = windowMs - (now - oldestHit)`.

Caveats that matter for a real client and for operators:

- Despite the docstring calling it a "fixed-window-per-minute limiter", the implementation is
  a **rolling window** — hits older than `windowMs` are dropped, so it is not reset on a clock boundary.
- Storage is per Node process, and the map is capped at `MAX_KEYS = 10_000` (stale keys evicted,
  then least-recently-seen). Behind several instances the limit becomes per-instance.
- Only `Retry-After` is emitted, and only on 429. The `limit`/`remaining` values are computed
  but never surfaced — there are **no `X-RateLimit-*` headers** anywhere in the codebase.
- `resetRateLimits()` exists for tests; there is no HTTP way to clear a bucket.

Guards: `requireRateLimitedUser(scope, limitPerMinute?)` in `src/lib/api.ts` = `requireUser()`
+ `checkRateLimit("<scope>:<userId>")`. It runs **before** body parsing, so a rejected body
still consumes a slot.

| Scope key | Limit | Applies to |
|-----------|-------|-----------|
| `chat:<userId>` | `CHAT_RATE_LIMIT_PER_MINUTE` (default 20) | `POST /api/chat` **and** `POST /api/chat/regenerate` (shared bucket) |
| `conversations:<userId>` | `API_RATE_LIMIT_PER_MINUTE` (default 120) | all 4 verbs of `/api/conversations*` |
| `models:<userId>` | 30 / min (hard-coded) | `GET /api/models` |
| `preferences:<userId>` | 60 / min (hard-coded) | `GET`/`PATCH /api/preferences` |
| `usage:<userId>` | 60 / min (hard-coded) | `GET /api/usage` |
| `upload:<userId>` | 20 / min (hard-coded) | `POST /api/attachments` |
| `export:<userId>` | 30 / min (hard-coded) | `GET /api/conversations/{id}/export` |
| `register:<ip>` | 10 / min (hard-coded) | `POST /api/auth/register` — keyed on the first `x-forwarded-for` entry, else `x-real-ip`, else `"unknown"` (`clientIp()` in `src/lib/session.ts`) |
| `login:<email>:<ip>` | 10 / 5 min (hard-coded) | Auth.js `authorize()`; not an HTTP 429 |

`POST /api/chat/stop` is the one authenticated route **without** rate limiting — it uses
`requireUser()` directly.

429 body and header:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 12
{ "error": { "code": "rate_limited", "message": "Too many requests" } }
```
(Chat and register override the message: "You are sending messages too quickly." /
"Too many sign-up attempts"; the generic guard says "Too many requests. Please slow down
before trying again.")

## DTOs

Field names are exactly as serialized; dates are ISO-8601 strings (`new Date().toISOString()`).

**`MessageDto`** — `src/lib/dto.ts`, client mirror `src/types/chat.ts`:

```json
{
  "id": "cm...", "role": "user", "content": "text",
  "status": "COMPLETED",
  "model": "qwen2.5:3b", "error": null,
  "suggestedFollowUps": ["…"],
  "createdAt": "2026-11-05T02:00:00.000Z",
  "usage": { "promptTokens": 12, "completionTokens": 240, "latencyMs": 4200 },
  "attachments": [ { "id": "cm…", "fileName": "notes.md", "mimeType": "text/markdown", "sizeBytes": 912 } ]
}
```

- `role` is lower-cased on the wire (`user|assistant|system`); `status` is **upper-case**
  (`STREAMING|COMPLETED|CANCELLED|FAILED`) — the DB enum passes through unchanged.
- Token/latency numbers are `null` until a turn is finalised.
- Attachments are joined in the query but `createdAt` is deliberately dropped from the DTO.

**`ConversationSummaryDto`**: `{ id, title, model, createdAt, updatedAt, messageCount }`.
`messageCount` comes from Prisma's `_count.messages`, which only `listConversations()` selects.
In `POST /api/conversations`, `GET /api/conversations/{id}` and `PATCH …`, the field is
therefore always **`0`**, never an error.

**`PreferencesDto`**: `{ model, temperature, maxOutputTokens, systemPrompt, sendOnEnter, contextWindow }`.

**`ModelsDto`**: `{ provider, models, defaultModel, currentModel, limits: { temperature: {min,max}, maxOutputTokens: {min,max}, maxInputChars, maxUploadBytes } }`.

**`UsageDto`**: `{ days, totals: { messages, conversations, promptTokens, completionTokens, totalTokens, failed, cancelled }, perModel: [...], perDay: [...] }`.

## SSE protocol (`/api/chat`, `/api/chat/regenerate`)

`src/lib/ai/sse.ts` frames each event as:

```
event: <type>\ndata: <JSON of the whole event, including its "type"> \n\n
```

Response headers (from `SSE_HEADERS`):

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-store, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

There are no `id:` fields, no `retry:` field and no heartbeat comments — a stream that is slow
to start can be closed by an idle-timeout proxy (see `docs/DEPLOYMENT.md`).

The `event:` name and the JSON `type` are always identical, and the browser client
(`src/lib/sse-client.ts` + `src/hooks/use-chat.ts`) parses only the `data:` JSON. A third-party
client can therefore switch on either.

| Event | Payload | When |
|-------|---------|------|
| `meta` | `{ type, conversationId, userMessageId?, assistantMessageId, model }` | First, always. `userMessageId` is present on both chat and regenerate (the id of the user turn being answered). Lets the client swap its optimistic placeholder ids for DB ids. |
| `delta` | `{ type, text }` | One per provider chunk. `text` is a raw fragment — concatenation is the answer, no JSON, no re-markdown boundaries. |
| `title` | `{ type, title }` | Only when this was the conversation's first **user** message and the turn completed. Emitted after the body, since it needs a model call. Not sent by `/api/chat/regenerate` (`isFirstTurn: false`). |
| `followUps` | `{ type, items: string[] }` | Up to 3 items, only when non-empty and only on a completed turn. |
| `done` | `{ type, status: "COMPLETED"\|"CANCELLED"\|"FAILED", usage: { promptTokens, completionTokens, estimated, latencyMs } }` | Terminal on success and on cancellation. `estimated: true` means the provider gave no `usage`, so tokens were estimated (`src/lib/tokens.ts`: ~1 token per CJK char, ~4 chars per token elsewhere). |
| `error` | `{ type, code, message }` | Terminal on failure, **instead of** `done`. `code` is `"provider_error"` (upstream rejected/failed — message is sanitized, never the raw upstream body) or `"stream_failed"` (the generator itself threw; `chat.stream_crashed` is logged). |

Ordering on a healthy first turn: `meta` → `delta`* → `title` → `followUps`? → `done`.
On a cancelled turn: `meta` → `delta`* → `done{status:"CANCELLED"}`.
On a provider failure: `meta` → `delta`* → `error` (then the stream closes).

Errors raised *before* the stream opens are ordinary JSON envelopes (`401`, `429`, `422`,
`404`, `409`). Once HTTP 200 and `text/event-stream` are on the wire, all failures travel as an
`error` event.

## 1. `POST /api/chat`

`src/app/api/chat/route.ts`. Auth required. Rate limit `chat:<userId>`.

Check order: session → rate limit → body validation → conversation ownership → no active run →
settings resolution → persist user message → stream.

Body (`.strict()` — any extra key is a 422):

| Field | Type / limit | Required | Notes |
|-------|--------------|----------|-------|
| `conversationId` | string, 1–64 | yes | must belong to the caller, else 404 |
| `content` | string, trimmed, 1–`MAX_INPUT_CHARS` (default 16 000) | yes | empty after trim → "Message cannot be empty" |
| `attachmentIds` | array of id (1–64 each), **max 5** | no | `updateMany` scoped to `{ id: { in }, userId }`, so another user's ids are ignored silently |
| `model` | string, 1–120 | no | falls back through: request → conversation → preference/allowlist → `AI_DEFAULT_MODEL` (`resolveGenerationSettings`) |
| `temperature` | number, 0–2 | no | else preference |
| `maxOutputTokens` | int, 64–8192 | no | else preference |

Responses: **200** with `text/event-stream`; **401**, **404**, **409** (`generation_in_progress`),
**422**, **429**, **500** JSON.

A `STREAMING` assistant row is created before the provider is called, and the partial text is
persisted on completion, cancellation or failure (`run-turn.ts` → `finalizeAssistantMessage`).

```bash
curl -N -b cookies.txt -X POST http://localhost:3000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"conversationId":"cm8abc…","content":"Explain SSE in 3 bullets","temperature":0.2}'
```

`-N` disables curl's buffering so events print as they arrive.

## 2. `POST /api/chat/regenerate`

`src/app/api/chat/regenerate/route.ts`. Auth required. Shares the `chat:<userId>` bucket with
endpoint 1.

Body (`.strict()`): `conversationId` (1–64, required) plus the same optional `model` /
`temperature` / `maxOutputTokens`. No `content` field.

Behaviour: `deleteLatestAssistantTurn()` walks the transcript from the newest message backwards
and deletes the contiguous block of `ASSISTANT` rows at the tail, then returns the newest `USER`
row as the prompt. Responses: **200** SSE, **401**, **404**, **409** `nothing_to_regenerate`
(either "There is no assistant reply to regenerate" when the tail is not an assistant message,
or "There is no prompt to regenerate from" when the tail was deleted but no user turn remains),
**422**, **429**, **500**. `title` events are never emitted here.

```bash
curl -N -b cookies.txt -X POST http://localhost:3000/api/chat/regenerate \
  -H 'Content-Type: application/json' \
  -d '{"conversationId":"cm8abc…","model":"qwen2.5:3b"}'
```

## 3. `POST /api/chat/stop`

`src/app/api/chat/stop/route.ts`. Auth required, **no rate limit**.

Body: `{ "conversationId": string }` (1–64; the schema is declared inline in the route).
The conversation is ownership-checked first, so a foreign id is **404**.

```json
{ "stopped": true }
```

`stopped` is `false` when no run was registered for `runKey(userId, conversationId)` in this
process — already finished, or running on another instance (the active-run registry in
`src/lib/ai/active-runs.ts` is in-memory). Cancellation is bidirectional: this aborts the
provider request, and a client disconnect aborts it too (`stream-response.ts` listens on
`request.signal`). The partial reply is kept with status `CANCELLED`.

```bash
curl -s -b cookies.txt -X POST http://localhost:3000/api/chat/stop \
  -H 'Content-Type: application/json' -d '{"conversationId":"cm8abc…"}'
```

## 4. `GET /api/conversations`

`src/app/api/conversations/route.ts` + `listConversations()` in `src/lib/conversations.ts`.
Auth required, scope `conversations` (default `API_RATE_LIMIT_PER_MINUTE`).

Query (unknown keys ignored):

| Param | Type / limit | Default |
|-------|--------------|---------|
| `q` | string, max 120 | none — when set, matches `title` **or any message content**, `contains`, case-insensitive |
| `limit` | coerced int, 1–200 | 60 (re-clamped 1–200 in `listConversations`) |

Response: `{ "conversations": ConversationSummaryDto[] }`, ordered `updatedAt DESC, id DESC`.
**200**, or 401/422/429/500.

```bash
curl -s -b cookies.txt 'http://localhost:3000/api/conversations?q=nginx&limit=10'
```

## 5. `POST /api/conversations`

Body (`.strict()`): `{ "title"?: string }`, trimmed, 1–120. `{}` is valid — the row gets the
schema default `"New conversation"`. Response **201**:

```json
{ "conversation": { "id": "cm…", "title": "New conversation", "model": null,
                    "createdAt": "…", "updatedAt": "…", "messageCount": 0 } }
```

## 6. `GET /api/conversations/{id}`

`{id}` is validated by `conversationIdParams` (1–64) → 422 otherwise. Response:

```json
{ "conversation": ConversationSummaryDto, "messages": MessageDto[] }
```

Side effect worth knowing: `getConversationMessages()` first flips any `STREAMING` row in this
conversation to `CANCELLED`, because a server restart mid-generation leaves a row that will
never be written again. Messages come back `createdAt ASC, id ASC`, oldest first. The single
conversation object has no `_count`, so `messageCount` is `0` here. **404** if not owned.

```bash
curl -s -b cookies.txt http://localhost:3000/api/conversations/cm8abc…
```

## 7. `PATCH /api/conversations/{id}`

Body (`.strict()`, and **at least one key** must be present — the refine message is "Provide at
least one field to update"):

| Field | Limit |
|-------|-------|
| `title` | trimmed, 1–120 |
| `model` | string 1–120; if `AI_MODEL_ALLOWLIST` is set and the model is not in it → **400** `model_not_allowed` |

Response **200** `{ "conversation": ConversationSummaryDto }`. The model is stored but never
null-able through this endpoint (no explicit null support).

```bash
curl -s -b cookies.txt -X PATCH http://localhost:3000/api/conversations/cm8abc… \
  -H 'Content-Type: application/json' -d '{"title":"SSE debugging","model":"gpt-4o-mini"}'
```

## 8. `DELETE /api/conversations/{id}`

Response **200** `{ "deleted": true, "id": "cm…" }`. Rows cascade (messages, attachments,
`ON DELETE CASCADE`), and the uploaded bytes are removed from disk afterwards
(`deleteConversation()` → `rm(resolveUploadPath(storageKey), { force: true })`); a missing file
is swallowed so the delete never fails on it. Repeating the delete returns **404**.

## 9. `GET /api/conversations/{id}/export`

`src/app/api/conversations/[id]/export/route.ts`. Auth required, scope `export` (30/min).

Query: `format` = `markdown` | `json`, default `markdown`. Anything else → **422**
(the enum is applied via `parseInput`, so unknown extra params are ignored but `format` must be valid).

- `markdown` → `Content-Type: text/markdown; charset=utf-8`, `Content-Disposition: attachment; filename="<slug>.md"`.
  Body is `# <title>`, an export footer line with the ISO timestamp, message count and conversation id,
  then `## User` / `## Assistant` / `## System` sections. Empty messages render as `_(empty)_`;
  cancelled replies add `_Response stopped by user._`; failed ones add
  `_Response failed: <error>_`; attachments are listed by file name only.
- `json` → `Content-Type: application/json; charset=utf-8`, `filename="<slug>.json"`, 2-space-indented:

```json
{ "conversation": { "id": "…", "title": "…", "createdAt": "…", "updatedAt": "…" },
  "messages": [ MessageDto, … ] }
```

`<slug>` is the title lower-cased, non-alphanumerics collapsed to `-`, trimmed, capped at 48
chars, falling back to `conversation`. Note this route returns a `NextResponse` with an
attachment disposition, so it is a download, not an XHR-friendly payload.

```bash
curl -s -b cookies.txt -L -o chat.md \
  'http://localhost:3000/api/conversations/cm8abc…/export?format=markdown'
```

## 10. `POST /api/attachments`

`src/app/api/attachments/route.ts`. Auth required, scope `upload` (20/min).
`Content-Type: multipart/form-data` is mandatory → **415** `invalid_encoding` otherwise.

| Form field | Notes |
|------------|-------|
| `conversationId` | required, must be owned (404); the attachment is bound to it immediately |
| `file` | must be a `File` part |

Validation in `prepareUpload()` (`src/lib/uploads.ts`), in order: non-empty (400 `empty_file`);
`size <= MAX_UPLOAD_BYTES` (413 `file_too_large`, message reports whole MB); extension in the
allowlist (415 `unsupported_media_type`); no NUL byte in the first 1 KB (415 `binary_file`);
declared MIME must start with `text/` or be `application/json` / `application/xml` / empty
(415 `unsupported_media_type`).

Accepted extensions: `txt md markdown mdx csv tsv json jsonl ndjson yaml yml toml ini cfg conf
log html htm css scss xml sql js jsx ts tsx mjs cjs py rb go rs java kt scala c h cpp hpp cs php
swift sh bash zsh vue svelte graphql proto`.

Response **201**:

```json
{ "attachment": { "id": "cm…", "fileName": "notes.md", "mimeType": "text/markdown", "sizeBytes": 912 } }
```

- `fileName` is sanitized for display only (`basename`, then stripped to `[A-Za-z0-9._\- ()[\]]`,
  whitespace collapsed, capped at 120) — client names never reach the filesystem.
- Bytes go to `<UPLOAD_DIR>/<userId>/<uuid>.<ext>` with dir mode `0700`, file mode `0600`; the
  generated `storageKey` is what the DB stores.
- Text is extracted up to **200 000** chars into `extractedText`, with `textTruncated: true`
  beyond that. There is no read/download endpoint; the stored bytes are only re-read for deletion.
- Attachments become prompt context only when their ids are passed in a later
  `POST /api/chat`: `composeMessageContent()` inlines them as
  `Attached file "<name>": """…"""`, cutting each body at **12 000** chars.

```bash
curl -s -b cookies.txt -X POST http://localhost:3000/api/attachments \
  -F conversationId=cm8abc… -F file=@./notes.md
```

## 11. `GET /api/models`

`src/app/api/models/route.ts` → `buildModelsDto()` in `src/lib/models-dto.ts`.
Auth required, scope `models` (30/min). **200**:

```json
{
  "provider": "ollama",
  "models": ["qwen2.5:3b", "llama3.1"],
  "defaultModel": "qwen2.5:3b",
  "currentModel": "qwen2.5:3b",
  "limits": {
    "temperature": { "min": 0, "max": 2 },
    "maxOutputTokens": { "min": 64, "max": 8192 },
    "maxInputChars": 16000,
    "maxUploadBytes": 5242880
  }
}
```

`models` comes from the upstream `GET /v1/models`, is filtered by `AI_MODEL_ALLOWLIST` when set,
and always has `defaultModel` prepended and de-duplicated. If the upstream list call fails the
route still returns **200** with just `[defaultModel]` (the failure is logged as
`provider.model_list_failed`) — so an empty-looking picker means the provider is unreachable.
`limits.temperature` / `limits.maxOutputTokens` are hard-coded in `buildModelsDto` and match
`validation.ts`; `maxInputChars` / `maxUploadBytes` come from env.

```bash
curl -s -b cookies.txt http://localhost:3000/api/models
```

## 12. `GET /api/preferences`

`src/app/api/preferences/route.ts` → `getPreferences()`. Scope `preferences` (60/min).
Creates the row on first read (`ensurePreferences`). **200**:

```json
{ "preferences": { "model": "gpt-4o-mini", "temperature": 0.7, "maxOutputTokens": 2048,
                   "systemPrompt": "You are a helpful, precise assistant…",
                   "sendOnEnter": true, "contextWindow": 8000 } }
```

These are **resolved** values: `model` falls back to the server default when the stored
`defaultModel` is null or outside the allowlist, and `systemPrompt` falls back to
`DEFAULT_SYSTEM_PROMPT` (`src/lib/default-system-prompt.ts`) when blank.

## 13. `PATCH /api/preferences`

Scope `preferences` (60/min). Body (`.strict()` — `contextWindow` is **not** accepted):

| Field | Limit |
|-------|-------|
| `defaultModel` | string 1–120, or `null`, or omitted (`.nullish()`); outside `AI_MODEL_ALLOWLIST` → **400** `model_not_allowed` |
| `temperature` | number 0–2 |
| `maxOutputTokens` | int 64–8192 |
| `systemPrompt` | trimmed, max 4000, or `null` |
| `sendOnEnter` | boolean |

Unlike the conversation update schema there is no "at least one field" refine, so `{}` succeeds
(it upserts a row with defaults). Response **200** uses the **raw stored row**, not the resolver —
so `model` and `systemPrompt` can come back `null` here even though `GET` never returns `null`:

```json
{ "preferences": { "model": null, "temperature": 0.7, "maxOutputTokens": 2048,
                   "systemPrompt": null, "sendOnEnter": true, "contextWindow": 8000 } }
```

`contextWindow` in this response is just the DB default (8000); it is not writable through the
API and is what sizes each turn's token budget (`budgetTokens: settings.contextWindow`).

```bash
curl -s -b cookies.txt -X PATCH http://localhost:3000/api/preferences \
  -H 'Content-Type: application/json' \
  -d '{"temperature":0.4,"maxOutputTokens":4096,"systemPrompt":"Be terse."}'
```

## 14. `GET /api/usage`

`src/app/api/usage/route.ts`. Auth required, scope `usage` (60/min).

Query: `days` — read manually, not through zod. `Number(raw ?? "14")`, non-finite becomes 14,
then clamped to **1–90** (`days=0` → 1, `days=1000` → 90, `days=abc` → 14). The window starts at
midnight of `days-1` days ago in **server local time** (`since.setHours(0,0,0,0)`).

Scope is `{ conversation: { userId }, createdAt: { gte: since } }` on `Message`, so a user only
ever sees their own rows. **200**:

```json
{
  "days": 14,
  "totals": { "messages": 82, "conversations": 7, "promptTokens": 12000,
              "completionTokens": 48000, "totalTokens": 60000, "failed": 1, "cancelled": 2 },
  "perModel": [ { "model": "qwen2.5:3b", "messages": 82, "promptTokens": 12000, "completionTokens": 48000 } ],
  "perDay": [ { "date": "2026-10-23", "messages": 0, "tokens": 0 } ]
}
```

Read the caveats in the code before charting this: `totals.messages` counts **every role**
(user + assistant + system) in the window; `perModel` groups by the raw `model` column with
`null` shown as `"unknown"` and includes user rows; **`totals.conversations` is the user's
lifetime conversation count**, deliberately not filtered by `days`, so it is not comparable to
the other totals; `perDay` is pre-filled with a zero entry per calendar day in the window
(`toISOString().slice(0,10)`), so gaps are real gaps.

```bash
curl -s -b cookies.txt 'http://localhost:3000/api/usage?days=30'
```

## 15. `POST /api/auth/register`

`src/app/api/auth/register/route.ts`. **No session required.** Rate limit `register:<ip>`,
10/min. Password hashing: `bcrypt` cost **12**.

Body (`registerSchema` — a plain object, so **unknown keys are ignored**, unlike the other
routes):

| Field | Limit |
|-------|-------|
| `email` | trimmed, lower-cased, must be an email, max 254 |
| `name` | optional, trimmed 1–60 |
| `password` | 8–72 chars, must match `/[a-zA-Z]/` and `/[0-9]/` (72 is bcrypt's input limit) |

- **201** `{ "user": { "id", "email", "name", "createdAt" } }` — a `Preference` row is created in
  the same insert (`preferences: { create: {} }`). The password hash is never selected.
- **409** `email_taken` — "An account with this email already exists" (checked with a prior
  `findUnique`, so it is advisory under a race; the `User.email` unique index is the real guard).
- **422** per-field issues; **429**; **500**.

Registration is only the row. Sign-in is a separate step — the browser form calls
`signIn("credentials", …)` afterwards (`src/components/auth/auth-form.tsx`).

```bash
curl -s -X POST http://localhost:3000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"ada@example.com","name":"Ada","password":"correc…t1"}'
```

## 16. `/api/auth/[...nextauth]`

`src/app/api/auth/[...nextauth]/route.ts` is `export const { GET, POST } = handlers;` — Auth.js
owns everything below it. Subpaths you will actually hit: `GET /api/auth/providers`,
`GET /api/auth/csrf`, `POST /api/auth/signin`, `POST /api/auth/callback/credentials`,
`GET /api/auth/session`, `POST /api/auth/signout`, `GET /api/auth/error`. Their statuses,
redirects and cookie behaviour follow Auth.js v5, and this app does not add a custom adapter
(`Session` / `Account` / `VerificationToken` tables exist in `prisma/schema.prisma` but are
unused by the JWT strategy).

## Database shapes behind these responses

`prisma/schema.prisma` (Postgres, `prisma-client` generator emitting to `src/generated/prisma`,
driver adapter required). Enums: `MessageRole { USER, ASSISTANT, SYSTEM }`,
`MessageStatus { STREAMING, COMPLETED, CANCELLED, FAILED }`.

- `User` — `email @unique`, `passwordHash`, `name?`, timestamps; relations to
  `Conversation[]`, `Preference?`, `Attachment[]`, `Account[]`, `Session[]`.
- `Conversation` — `title @default("New conversation")`, `model?`, rolling context
  `summary? @db.Text` + `summaryCovers Int @default(0)`; indexes
  `(userId, updatedAt DESC)` and `(userId)`; `userId` cascade delete.
- `Message` — `role`, `content @db.Text`, `status @default(COMPLETED)`, `model?`,
  `promptTokens?`, `completionTokens?`, `latencyMs?`, `error?`,
  `suggestedFollowUps String[] @default([])`; indexes `(conversationId, createdAt)` and
  `(createdAt)`; conversation cascade delete.
- `Attachment` — `fileName`, `mimeType`, `sizeBytes`, `storageKey @unique`,
  `extractedText? @db.Text`, `textTruncated @default(false)`; `messageId?` with
  `onDelete: SetNull`; indexes on `messageId`, `userId`, `conversationId`;
  `conversationId` cascade.
- `Preference` — `userId @unique`, `defaultModel?`, `temperature @default(0.7)`,
  `maxOutputTokens @default(2048)`, `systemPrompt? @db.Text`, `contextWindow @default(8000)`,
  `sendOnEnter @default(true)`.
- `Account` (`@@unique([provider, providerAccountId])`, index `userId`),
  `Session` (index `userId`), `VerificationToken` (`token @unique`,
  `@@unique([identifier, token])`) — Auth.js scaffolding, unused at runtime.

Migrations (`prisma/migrations/`, provider `postgresql`):
`20261104185814_init` (both enums + all seven tables + indexes/FKs),
`20261104190830_conversation_model` (adds `Conversation.model`),
`20261104191315_attachment_conversation` (adds required `Attachment.conversationId` + index + FK —
this one is not safe on a non-empty `Attachment` table without a backfill).

## Client contract notes

- The browser never calls `EventSource` (it cannot POST); it reads `response.body` through
  `readSseStream()` (`src/lib/sse-client.ts`), splitting on `\n\n` and taking the `data:` lines.
- `useChat` (`src/hooks/use-chat.ts`) renders optimistic ids (`pending-user-*`,
  `pending-assistant-*`) and swaps them on the `meta` event; on `meta` it also clears the
  optimistic attachment chips, because the server re-links them by id.
- A non-2xx JSON response before streaming is shown from `error.message`, and a **401**
  redirects the browser to `/login`.
- `GET /api/models` and `GET /api/preferences` are also consumed on the server by
  `src/app/chat/layout.tsx` via `buildModelsDto()` / `getPreferences()` — those code paths bypass
  HTTP and the rate limiter.
